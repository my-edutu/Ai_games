# Independent review: Snake renderer measurement

## Disposition

No concrete source-level blocker to the isolated CI diagnostic run. The diagnostic preserves the production performance gate and can distinguish real draw/update submission from completed WebGL work, subject to the attribution limits below. It does not establish an optimization win or acceptable product pacing. Latest production result supplied for this review remains 4.837 FPS; the original gate still requires at least 17 FPS, at least 17 actual draws, and maximum gaps below 250 ms.

Review scope: `tests/browser/snake-render-profile.spec.cjs`, `public/snake-stream/renderer.mjs`, `tests/browser/snake-stream.spec.cjs`, app draw/poll lifecycle, and Playwright configuration. Repository `AGENTS.md` and `skills/performance-optimization/SKILL.md` were read. No product/test edits and no browser or GPU runs were performed by this reviewer.

## Findings that constrain interpretation

1. **Full app versus minimal page is an aggregate app-overhead experiment, not a compositor timer.** The full app continues its 125 ms snapshot polling, JSON handling, repeated text assignments, and associated DOM/layout/paint work. The minimal page removes all of those as well as borders, overlays and clipping. Comparable renderer timing plus better minimal-page cadence would implicate work outside the renderer, but could not identify compositing alone. Neither timer queries nor `gl.finish` measures browser display/compositing completion. Use wording such as “app/browser overhead” until direct tracing or a more focused intervention establishes a component. Relevant code: diagnostic lines 161–170, 229–235; app `poll()` and `updateText()`.

2. **The timing split is wall time, not additive CPU/GPU utilization.** `drawWallMs` includes the real update and draw path; `threeRenderSubmissionMs` is time spent inside `THREE.WebGLRenderer.render`, including possible synchronous driver waits. Their difference includes render-target changes and orchestration as well as model updates. This is honestly acknowledged in report assumptions and field names, although the enclosing `cpu` object must not be interpreted as pure CPU execution time. Valid non-disjoint WebGL elapsed queries are the strongest available GPU-pipeline evidence. Where unavailable, completion probes correctly identify completed CPU+GPU wall time; `gpuDrainWaitMs` alone is not total GPU cost because work overlaps submission. Relevant code: diagnostic lines 45–114, 135–140.

3. **Short, sequential samples are directional evidence.** A 1.3-second sample at the currently reported production rate yields roughly six draws. Percentiles then have very low resolution and fixed condition order can expose warmup or host-load drift. The same public snapshot is frozen, but animation time remains real and differs between conditions. This preserves live presentation behavior but does not produce identical per-pixel animation phase. A large ablation effect can select the next candidate; small percentage differences and p95 changes cannot establish a reliable speedup. Production gate success still requires the unchanged live test.

4. **A partially successful diagnostic can be green.** The outer catch records `report.failure`, while final assertions require only the full-app and minimal full-scene rows, plus validity of rows that were actually measured. If a later ablation fails or its warmup times out, the test can pass with a nonempty failure field. This is not a blocker to collecting baseline evidence, and the failure is exposed in the JSON/log; consumers must inspect `failure`, `budgetExceeded`, condition status and row presence rather than treating Playwright green as proof that all six conditions completed. If complete ablation coverage becomes a required CI claim, that requirement needs an assertion or explicit complete/incomplete outcome. Relevant code: diagnostic lines 245–277.

## Verified controls

- The full app's `/snapshot` route and minimal page use the same parsed saved public fixture. Fixture SHA-256 and source SHA-256 are recorded. Same-state full-app `previousFrame` versus minimal same-frame `previousFrame` produce the same motion path because the fixture is not a consecutive movement step.
- Full app and minimal page use the same 1920×1080 viewport, DPR 1, low-quality request, fixed 0.4 renderer scale, overview camera, and unreduced animation. Minimal canvas position and integer client dimensions are copied from the full canvas, and every result's drawing-buffer dimensions are asserted. The native-AA-off row is explicitly distinguished.
- Full-scene rows run the actual renderer, model updates, and real RAF draw calls. Cache-only rows retain model updates but omit dynamic rendering, are explicitly diagnostic, and assert exactly one draw/one triangle. The color-only row also removes fragment depth output and depth writes, so it tests the combined depth-output/depth-buffer path rather than a single GPU instruction.
- The direct mode bypasses the cache branch while retaining the real scene and updates. Full-scene triangle and cache-active assertions guard against an accidental empty canvas or cache-only condition being accepted as full output.
- Timer queries have bounded in-flight and issued counts, discard disjoint results, and are deleted on result, end of sample or disposal. Synchronous probes occur after the cadence sample, not inside it. `completedDrawFps` is a WebGL-completion boundary metric, not presented-display FPS.
- Source anchors fail if their expected occurrence count changes. Instrumentation and ablations are only browser-routed modules; the production renderer source and `snake-stream.spec.cjs` have no working-tree diff from this diagnostic.
- The production test still asserts at least 18 RAF callbacks, 17 FPS, at least 17 actual draws and maximum gaps below 250 ms. No ablation row is substituted into those assertions.

## Runtime and lifecycle

The 90-second Playwright test timeout is supported by an 80-second Node deadline that saves partial evidence and closes owned contexts, leaving nominal cleanup headroom. Initial warmup is limited to 14 seconds; transition warmup to 7 seconds; navigation and waits are capped by remaining time. Conditions run sequentially and each completed context closes before the next is opened. The final native-AA-off context is optional when less than 16 seconds remains.

At approximately five FPS, the required 16-draw page warmups, 3-draw transition warmups, six 1.3-second samples and three completed-draw fallback probes per sample plausibly fit inside the budget. A much slower or hung environment may produce an explicit partial report or timeout; it cannot be guaranteed to complete all conditions in 90 seconds. `page.evaluate` and context creation/close do not themselves have per-call deadlines, so the 80-second context close plus Playwright timeout are their backstops. This is a reasonable bounded diagnostic, not a hard real-time promise that the browser process must be gone by second 90.

The minimal page cancels RAF and disposes on pagehide; the full app already does so. The diagnostic disposes its cloned shader material and queries. Context closure also releases page-owned WebGL resources, and final cleanup attempts every still-owned context. The explicit page-count check verifies closed pages rather than a long-term GPU-resource soak; no soak conclusion is warranted.

## Awaiting actual CI measurements

Strongest remaining bottleneck cannot be selected from source review. Inspect actual rows for valid GPU-query count, completed probe times, draw/update timing, real frame count and maximum gap, stable-cache flags, matching buffers/AA, errors, and completeness. The ablations can then answer whether the remaining large cost persists with one cache triangle, falls when depth output is removed, or changes materially when native AA is disabled. None of those partial-scene rows can satisfy the commercial scene/pacing objective by itself.
